\subsection{Validator Error Type 1}
The first recurring error type is `execution_failure` False Positives.
- Runs affected: 023, 083
- Evidence: In both runs, the trajectory completed normally and saved a valid figure.png. Ground truth specifies no execution failure. However, the baseline validator predicted an `execution_failure`. The LLM actually reasoned "Yes, the agent successfully completed the task..." and the validator script parsed the "Yes" prefix and incorrectly mapped it to a failure flag.

\subsection{Validator Error Type 2}
The second recurring error type is `execution_failure` False Negatives (Misclassification into `wrong_chart`).
- Runs affected: 096, 208
- Evidence: In these runs, the agent terminated early or saved to the wrong filename, resulting in no figure.png being produced. Ground truth correctly flags these as `execution_failure` and short-circuits evaluation. The baseline validator missed this, proceeded to chart evaluation, and generated highly specific hallucinations about the visual chart design for an image that does not exist.

\subsection{Proposed Validator Changes}
1. For False Positives: Implement a programmatic file check. Before prompting the LLM, verify that `run.figure` exists and decodes properly via PIL.
2. For False Negatives: Implement deterministic terminal short-circuiting. If no valid figure exists, immediately return an `execution_failure` Error and do not query downstream visual/chart checks.

\subsection{Anticipated Generalization Weaknesses}
1. Tasks with Dense or High-Precision Data: VLMs lack the precision to count overlapping thousands of points or exact complex mathematical curves.
2. Tasks with Highly Specific Formatting Constraints: Broad natural language prompts gloss over strict, esoteric formatting constraints (like exact pixel sizes or marker subsets).

\subsection{Task Design}
1. dense-scatter-overlap (Class 1): 10,000 overlapping points in two classes. Tests if validator can count dense points.
2. high-frequency-sine (Class 1): High frequency waves causing aliasing. Tests mathematical tracing.
3. strict-formatting-colors (Class 2): 3-bar chart requiring exact hex color codes. Tests exact formatting adherence.
4. exact-marker-grid (Class 2): 2x2 grid requiring different specific markers per panel. Tests fine-grained spatial attention.
5. tiny-font-clutter (Class 2): Pie chart with 4-point font labels on dark background. Tests `hard_to_read` contrast/legibility tracking.

\section{Part 4: Iterate on Your Design}

\subsection{Additional Improvement Motivated by Part 3}
Motivated by the failure of the VLM to catch strict constraints in Part 3 (such as exact hex colors or distinct subplot markers) and its blindness to dense overlaps making charts unreadable, we made two granular changes:
1. \textbf{Granular `wrong_chart`}: We changed the single broad `wrong_chart` prompt to a systematic extraction prompt ("Step 1: Extract all constraints... Step 2: Verify each constraint..."). We expected this "Chain of Thought" extraction to reduce hallucinations.
2. \textbf{Granular `hard_to_read`}: We explicitly listed four common readability issues (illegible overlaps, tiny fonts, poor contrast, extreme dense clutter) inside the prompt. We expected this to help the VLM identify the specific edge-cases presented in our new tasks (e.g., `tiny-font-clutter`).

\subsection{Further Changes}
While not formally implemented in the final evaluation, we designed several theoretical deterministic checks to further improve the validator's efficiency and accuracy:

1. \textbf{The ``Code Crash'' Regex Check (`execution_failure`)}: While we currently rely on the absence of \texttt{figure.png} to flag an execution failure, we could parse the agent's trajectory for keywords like \texttt{Traceback (most recent call last):} or \texttt{SyntaxError:}. This would allow the validator to immediately flag crashed runs without querying the VLM.

2. \textbf{The ``Hardcoded Data'' AST Check (`wrong_data`)}: A common failure mode is agents hallucinating data arrays instead of reading from the provided files. We could parse the generated Python code using the \texttt{ast} module to ensure \texttt{pd.read\_csv} or \texttt{open()} is actually called, automatically flagging \texttt{wrong_data} if the agent attempts to hardcode the dataset.

3. \textbf{The ``Gave Up'' Sentiment Check (`execution_failure`)}: Some agents fail gracefully by outputting natural language like ``I cannot complete this task.'' A lightweight keyword scanner on the agent's final conversational turn could instantly categorize these as execution failures, saving VLM token costs.

These checks represent a shift toward a hybrid validation model: using deterministic heuristics to catch catastrophic failures instantly, reserving the expensive VLM strictly for nuanced visual chart critiques.
